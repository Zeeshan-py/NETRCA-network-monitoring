# Phase 8 anomaly detection

Phase 8 analyzes validated Phase 6 metric records without changing monitoring, evidence collection, fault injection, or the database schema. Only the local backend can call these endpoints. `POST /api/v1/anomalies/detect` also requires `X-NetRCA-Local-Control: 1`. Set `NETRCA_ANOMALY_WRITES_ENABLED=true` to allow persistence; the default is `false`.

Supported metric types are `LATENCY` (ms), `PACKET_LOSS` (%), `AVAILABILITY` (%), `INTERFACE_STATE` and `LINK_STATE` (0=down, 1=up), and `RX_ERRORS`/`TX_ERRORS` (cumulative packet counters). Other cumulative counters cannot establish a rate from one sample and are not analyzed. Missing values are never replaced with zero. The detector accepts only non-future, timezone-aware Phase 6 observations. Observations older than 60 minutes return `INSUFFICIENT_DATA` by default. For counters, a prior sample of the same resource and interface is required; a counter decrease is treated as a reset, not an anomaly.

Default threshold violations are latency **>100 ms**, packet loss **>5%**, availability **<99%**, state **down**, and an error-counter increase of **at least 1**. Equal-to-limit latency/loss/availability values are normal. Threshold decisions need no learned history. For latency and loss below their absolute limits, at least 20 distinct prior observations of the same resource, metric, interface and target within 24 hours form a robust baseline. The median and median absolute deviation (MAD) give an upper limit `median + max(4 × 1.4826 × MAD, floor)`, with a 5 ms latency floor or 0.5 percentage-point loss floor. Only increases are harmful baseline deviations. Duplicate keys and duplicate timestamps do not increase sample count; conflicting values at one timestamp are excluded from the baseline.

An optional one-feature [Isolation Forest](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.IsolationForest.html) uses at least 50 distinct prior observations with at least five different values. It fits **only prior observations**, never the candidate. The fixed seed is 41, 64 trees, one job, and the configurable contamination defaults to 0.05. A negative `decision_function` margin indicates an outlier; lower latency/loss is excluded. If scikit-learn is unavailable, history is sparse, or the data is too uniform, threshold and robust-baseline decisions still work. The package is declared in `backend/requirements.txt`; installing dependencies in the development venv enables this path.

Results are `NORMAL`, `ANOMALY`, or `INSUFFICIENT_DATA`. `reason`, `method`, `support`, `baseline_samples`, and the source measurement make the decision inspectable. A score is a **method-specific strength**, not a probability or calibrated confidence: threshold score is the fractional limit violation capped at 1, baseline score is the amount above its robust upper limit divided by its allowed deviation and capped at 1, error-counter score is delta divided by ten times the configured threshold and capped at 1, and Isolation Forest score is the empirical fraction of baseline margins at least as normal as the candidate. A normal threshold/baseline result has score 0; insufficient data has no score. Severity is assigned only to anomalies: threshold/baseline exceedance factor below 1.5 is LOW, 1.5–<2 MEDIUM, 2–<5 HIGH, and ≥5 CRITICAL; a down state is HIGH. This classification is a rule, not a prediction of business impact.

`POST /api/v1/anomalies/detect` accepts exactly one of:

```json
{"metric_ids":["<stored-metric-uuid>"],"persist":true}
{"observations":[{"device_id":"<device-uuid>","metric_type":"LATENCY","value":120,"unit":"ms","timestamp":"<UTC timestamp>","source":"manual","observation_key":"manual:unique-key"}]}
```

At most 20 stored IDs or 20 inline observations may be analyzed per request. Inline data is **unverified caller input**; it is never inserted into Phase 6 metrics or the anomaly table, even if the client supplies a resource UUID. It remains useful for local threshold and baseline analysis when PostgreSQL is unavailable. Stored IDs require the existing database; only validated Phase 6 rows with source and observation-key metadata are analyzed. Historical queries are limited to 100 rows per candidate by default. Repeated IDs and copies of the same inline observation are counted once; a repeated key with conflicting content returns 409.

Persisted anomalies use the existing `public.anomalies` table, referencing their source metric. Normal and insufficient results are not inserted. Writes lock the source metric row and reuse an existing anomaly with the same metric, method and configuration version, so repeated detection does not create another row through this service. Each result reports `persistence`: `PERSISTED`, `EXISTING`, `UNAVAILABLE`, `NOT_ELIGIBLE`, or `NOT_REQUESTED`. A write failure never appears as successful persistence. `GET /api/v1/anomalies`, `GET /api/v1/anomalies/{id}`, and `GET /api/v1/anomalies/statistics` read stored records with bounded pagination and safe 503 errors when the database is unavailable.

Settings in `backend/.env.example` configure all thresholds, observation age, history window/count, baseline minimum, and Isolation Forest minimum/contamination. Test on Windows with `backend/.venv/Scripts/python.exe -m pytest backend/tests -q` from the repository root. In Ubuntu WSL2, set `NETRCA_RUN_MININET_TESTS=1 NETRCA_RUN_FAULT_TESTS=1` and run the backend suite with the Linux venv as root. The PostgreSQL rollback test requires separate `NETRCA_RUN_ANOMALY_DB_TESTS=1` and a reachable configured database. Synthetic unit fixtures are not real network observations. Anomaly detection does not create Phase 9 correlated events, RCA findings, or automatic faults.
