# NetRCA — Product Requirements Document (PRD)

## 1. Product Overview

**Product Name:** NetRCA  
**Full Name:** AI-Powered Network Root Cause Analysis and Incident Response System

NetRCA is an AI-powered network monitoring and root-cause analysis platform that observes a simulated network, detects abnormal behavior, correlates network events, identifies the most probable root cause of an incident, analyzes its impact, and provides actionable recommendations.

The system will use **Mininet** to create and simulate the network, **Python and Scikit-learn** for data processing and anomaly detection, **NetworkX** for topology and relationship analysis, **Gemini API** for AI-powered explanation and recommendations, **FastAPI** for the backend, **Supabase/PostgreSQL** for persistent data storage, and **React/Next.js with Tailwind CSS** for the dashboard.

---

## 2. Problem Statement

Traditional network monitoring tools can report individual symptoms such as high latency, packet loss, server timeout, or interface errors. However, multiple symptoms may actually be caused by one underlying failure.

For example:

Router R1 interface failure
→ packet loss
→ increased latency
→ server timeout
→ service disruption

NetRCA aims to move beyond simply reporting symptoms by correlating metrics, logs, events, timestamps, and network topology to identify the most probable root cause and explain the incident.

---

## 3. Product Goal

The primary goal is:

> **Observe → Detect → Correlate → Diagnose → Explain → Recommend**

NetRCA should answer:

1. What is happening?
2. Is the behavior abnormal?
3. Which components are affected?
4. What events are related?
5. What is the probable root cause?
6. How did the failure propagate?
7. What is the impact?
8. What should the administrator do?

# 13. Root Cause Analysis

The RCA engine will identify the most probable underlying cause of an incident.

### RCA Inputs

- Network metrics
- Logs
- Events
- Timestamps
- Network topology
- Anomaly results
- Device relationships
- Failure propagation sequence

### RCA Output

```text
Root Cause:
Router R1 interface failure

Confidence:
92%

Affected Components:
S1
Server1
Server2

Evidence:
- R1 error occurred first
- Packet loss started immediately afterward
- Downstream devices were affected

```

### Important Rule

The system should distinguish between:

**Symptom**
- High latency
- Packet loss

# 16. Gemini AI Integration

Gemini API will be used as the AI explanation and recommendation layer.

### Gemini Responsibilities

- Explain detected incidents
- Summarize the root-cause analysis
- Explain the failure chain
- Generate human-readable incident reports
- Provide recommended troubleshooting actions
- Explain technical findings in simple language
- Answer questions about the current incident

### Example

**System finding:**

```text
Root Cause = R1 interface failure
Confidence = 92%
```

Gemini converts this into:

> Router R1 appears to be the most probable root cause. Its interface failure occurred before the packet loss and latency increase, and the topology shows that downstream servers depend on this path. Inspect the R1 interface and routing configuration.

Gemini should **not be the only source of root-cause detection**. The deterministic/ML RCA pipeline will provide evidence, while Gemini explains the findings and produces recommendations.

# 24. Explainable AI

NetRCA should not simply output:

> "Router R1 failed."

It should show why.

### Evidence-based explanation

```text
Root Cause: R1 interface failure
Confidence: 92%

Evidence:
1. R1 error occurred first.
2. Packet loss increased immediately afterward.
3. Latency increased after packet loss.
4. Downstream servers became unavailable.
5. R1 is an upstream dependency in the topology.
```

This improves transparency and makes the AI decision easier to understand.

# 31. Security and Safety

NetRCA is intended for a simulated environment.

### Requirements

- No unauthorized network scanning
- No automatic modification of real networks
- No destructive actions against real infrastructure
- Fault injection must operate only inside the controlled Mininet environment
- AI recommendations should be human-reviewed
- API keys must be stored securely as environment variables
- Supabase credentials must not be exposed in frontend source code

---

# 32. Non-Functional Requirements

### Performance
- Dashboard should update network information with low latency.
- Incident detection should occur shortly after abnormal behavior appears.

### Reliability
- Network failures should not crash the monitoring backend.
- Historical incident data should remain available.

### Usability
- Dashboard should be understandable without reading source code.
- Root-cause results should include evidence.

### Scalability
The architecture should allow additional devices, metrics, fault types, and ML models to be added later.

### Maintainability
Backend, ML, RCA, network simulation, and frontend should be separated into modules.
